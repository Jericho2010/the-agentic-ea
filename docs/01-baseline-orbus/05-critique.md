# 1.5 — Critique of Orbus Infinity

A fair critique distinguishes **practice failures** from **product limitations**.

## What remains valuable

1. **Shared executive objects** — Capabilities and applications as meeting vocabulary.
2. **Governance theater that sometimes works** — ARB intake and decision history beat Slack amnesia.
3. **Connector intent** — Recognizing that EA dies without CMDB/cloud feeds.
4. **Metamodel pruning** — CoreEA’s instinct is correct even if the store is closed.

## Structural limitations

| Limitation | Consequence |
|---|---|
| Proprietary metamodel store | Agents/CI cannot validate the same schema in Git |
| Weak inner-loop presence | Developers update architecture after delivery—or never |
| Declared models lag reality | Cloud sprawl and microservice churn outpace repository edits |
| Analytics ceiling | Not a Spark/SQL engine for FinOps-scale or process mining |
| Diagram verification gap | Views are not deterministically compiled/tested |
| Vendor packaging lock | Skills and content become Orbus-shaped, not portable |

## Organizational failure modes (not uniquely Orbus)

- EA team as diagram factory
- CMDB sync without entity resolution → garbage-in
- ARB as bureaucracy without automated gates
- “Single source of truth” claims without runtime evidence

## Critique summary for modernization

Orbus Infinity fails modern delivery when treated as the **system of enforcement**. It can still serve as a **system of collaboration** during transition. The modernization target is:

**Git-validated PAM + lakehouse facts + agent enforcement + Archify rendering (± Orbus coexist).**
